1. What This System Is

Bedlay Gardens is a single Next.js application (a monolith, not microservices) serving a single-site dog boarding/day-care business. One deployment, one Postgres database, four route-grouped applications inside it:

  • Marketing site (src/app/(marketing)) — public pages, booking wizard entry point, login/register.
  • Customer portal (src/app/portal) — authenticated customer self-service.
  • Staff app (src/app/staff) — operational tools for kennel/day-care staff.
  • Admin back office (src/app/admin) — management, pricing, reporting, content.

There is no separate backend service and no message queue — everything is synchronous request/response, either through Next.js Server Actions (the primary mutation surface) or a small set of true HTTP route handlers.

  • Booking core: Service, Dog, DogMedication, DogFeedingItem, DogFlag/DogFlagType, VaccinationRecord, KennelUnit, KennelOccupancy, Booking, BookingDog, Addon, BookingAddon, BlockedDate
  • Payments: Payment, Voucher, CreditLedger, PriceRule, Subscription

  • Content/CMS: MediaItem, GalleryCategory, Testimonial, Faq, Setting
  • Notification: ContactMessage, EmailLog, SentEmail, EmailTemplate, NotificationPreference, MessageLog
  • Compliance: AuditLog, Agreement, SignedAgreement, Review, WaitlistEntry

Concurrency safety

KennelOccupancy has a @@unique([kennelUnitId, date]) constraint — this is what makes kennel double-booking structurally impossible, not just application-level checking. Day-care/meet-greet capacity uses SERIALIZABLE-isolation transactions with retry (MAX_ATTEMPTS = 5, 3 call sites) rather than a unique constraint, since capacity there is a count, not a 1:1 slot. tests/e2e/concurrency-race.spec.ts directly exercises this behavior — the strongest available corroboration that the design works as intended.

BookingStatus state machine (9 values)

DRAFT → PENDING_PAYMENT/PENDING_VACCINATION → CONFIRMED → CHECKED_IN → CHECKED_OUT → COMPLETED, with CANCELLED_BY_CUSTOMER / CANCELLED_BY_ADMIN / NO_SHOW as terminal states reachable from various points. There is no formal state-machine table in the codebase — this is assembled from reading the relevant modules (payment-timing, vaccination-gate, staff check-in/out actions, the Stripe webhook, and the abandoned-booking-recovery cron).

6. Authentication & Authorization Model

  • Authentication: NextAuth v5 (beta) — Credentials (email + bcrypt) and Resend magic-link providers, JWT session strategy.
  • Session lifetime: no maxAge/updateAge override → library defaults apply (30-day idle expiry, refreshed at most once per 24h of activity). Role/isSuperAdmin/other claims are written into the JWT only at sign-in and never re-read from the database afterward — deactivating, demoting, or password-resetting a signed-in user does not end their existing session early.
  • Route gating: centralized in src/auth.config.ts's authorized callback, enforced by src/proxy.ts's matcher (/admin/:path*, /staff/:path*, /portal/:path*). /admin requires role === "ADMIN"; /staff requires STAFF or ADMIN; ​/portal requires only being logged in — no role check. Role is a flat 3-value enum with no hierarchy; portal data is protected by per-resource ownership checks, not by role.
  • Critical gap — Server Actions and API routes are NOT covered by the middleware. Each must self-check auth()/a require*() helper. This is duplicated ad hoc across 20+ near-identical definitions rather than one shared, testable module.

Confirmed live authorization bypass: resolveBookingCreation in src/app/(marketing)/book/actions.ts (line 150) is exported from a "use server" module with no auth() call, taking a caller-supplied customerId plus admin-only safety-override parameters (skipVaccinationGate, overrideCompatibilityFlags). Because every export of a "use server" module is a directly callable endpoint regardless of who imports it internally, this is reachable directly — independently confirmed by a specialist security review as High severity. This should be fixed (move the shared logic to a plain src/lib/ module with no directive), not just documented.

Super-admin bootstrap: the first admin action is allowed when zero super admins exist system-wide — a one-time self-elevation window that closes itself once a super admin exists, but is open by default on any fresh/staging/restored environment.

7. Storage & File Handling

Two Cloudflare R2 buckets:

  • Private bucket — vaccination certificates, dog photos, agreements, pupdate media. Served only through /api/files/[...key], which enforces session + per-category ownership before proxying.
  • Public bucket — gallery/hero/content media, and also staff photos and agreement template PDFs (world-readable by design at the public R2 base URL).

Legacy local upload directories (storage/uploads/, public/uploads/) exist in the repo but are confirmed dead — zero code references anywhere. Path-traversal safety is enforced via assertSafeKey() (rejects .. and leading /) plus filename sanitization.

All four carry an identical Bearer $CRON_SECRET guard that fails closed (returns 400) if the secret is unset — meaning a misconfiguration silently stops these jobs rather than crashing loudly, which is worth including in any operational monitoring checklist since there is no error-tracking/alerting integration in this codebase to catch it otherwise.

9. Payments

Stripe handles deposits, balances, invoices, subscriptions, and refunds. The webhook (/api/webhooks/stripe) verifies signatures correctly and handles: checkout.session.completed, payment_intent.succeeded, payment_intent.payment_failed, charge.refunded, invoice.paid, invoice.payment_failed, invoice.voided, invoice.marked_uncollectible. There is no explicit idempotency check against Stripe's event.id — each handler instead relies on its own state check (e.g. if (payment.status === "SUCCEEDED") return), a reasonable but implicit strategy worth documenting explicitly for anyone modifying webhook handlers.

Vouchers and account credit use a read-then-write pattern at default (READ COMMITTED) isolation with no row lock or status predicate on the write — unlike the booking-capacity path, which correctly uses SERIALIZABLE + retry. This is a concurrency gap on the payment side flagged by the security review as a double-spend risk under simultaneous redemption.

10. Security Posture Summary

Full severity ratings and remediation guidance live in the companion security review; this section states only the architecturally load-bearing facts.

Confirmed working: no SQL injection surface (no raw queries), Stripe signature verification reads the raw body correctly, payment amounts are always recomputed server-side, HTML sanitization is a tight allowlist applied at both save and render, the private-file proxy's ownership model is correct across every upload call site.

Confirmed gaps: the resolveBookingCreation authorization bypass (§6); session claims never re-validated against the database; no rate limiting anywhere in the codebase (login, password reset, contact form, and the AI-extraction endpoint are all unthrottled); the auth library is on a floating prerelease version; a voucher/credit double-spend race under concurrent redemption; CSV exports use unescaped-formula-safe quoting but not full CSV-injection neutralization for =/+/-/@-prefixed values.

CSP (next.config.ts, applied to every route): script-src 'self' 'unsafe-inline' (plus 'unsafe-eval' in dev only), enumerated frame-src allowlist (Google, YouTube, Vimeo), object-src 'none', frame-ancestors 'none', plus HSTS with preload. The 'unsafe-inline' script/style allowance is a documented, deliberate tradeoff (JSON-LD structured-data tags and the admin rich-text editor's inline color swatches) rather than an oversight.

Body-size configuration gotcha

next.config.ts sets experimental.serverActions.bodySizeLimit: "200mb" and experimental.proxyClientMaxBodySize: "200mb" — both are required together because src/proxy.ts buffers request bodies independently at a 10MB default; setting only one causes large uploads (photos/video) to fail with a generic form-parsing error before reaching the Server Action.

Build & deploy

npm run build runs node scripts/warm-db.mjs && prisma migrate deploy && next build. There is no CI pipeline — .github/workflows/ exists but is empty, so there is no automated build/lint/test gate before a Vercel deploy beyond Vercel's own build step.

12. Known Technical Debt & Recommendations

Fix first

  1. resolveBookingCreation's missing auth() check (§6) — a live authorization gap, not just a documentation gap.
  2. Dependency versions: next-auth/@auth/core on a floating prerelease and next@16.2.10 both carry advisories relevant to this codebase's exact patterns; a non-major upgrade path exists.

Address soon

  • Extract one shared requireRole()/requireAdmin()/requireStaff() helper to replace the 20+ near-duplicate ad hoc checks — this is the structural root cause of gap #1 above.
  • Split src/app/(marketing)/book/actions.ts (953 lines, 5 service types' worth of booking logic in one file) into per-service modules.
  • Add rate limiting to public-facing forms and auth endpoints.
  • Fix the voucher/credit double-spend race with the same SERIALIZABLE+retry pattern already used for booking capacity.

Lower priority / awareness only

  • Remove the dead storage/uploads//public/uploads/ directories to avoid confusion with the R2-only storage model.
  • No ServiceType enum exists — the five service slugs are hard-coded string literals in the booking-creation branching logic, so a sixth Service an admin creates would get pricing/listing but no corresponding booking-creation branch until code is added.
